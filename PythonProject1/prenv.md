一、先明确：哪些功能真正需要算力？
你的项目可以拆成这条链路：
上传发票、行程单、审批单 → 识别内容 → 抽取字段 → 查询制度、预算和历史记录 → 执行审核规则 → 输出审核报告。

不同环节需要的环境不同：
功能	主要依赖	是否需要 GPU
上传文件、任务查询、人工复核	Python 后端、文件存储、数据库	不需要
金额、日期、审批和超标检查	Python 规则引擎	不需要
预算查询、重复发票检查	关系数据库、企业系统接口	不需要
图片文字识别	OCR 服务或本地 OCR	云服务不需要；本地可用 CPU
字段抽取、业务语义分析、报告生成	大模型	调用 API 不需要；本地运行通常需要
制度条款、相似案例检索	Embedding 模型、向量检索	小规模可以不需要


所以，这个项目不是所有审核都交给大模型，也不是必须有显卡才能开发。 这也符合你框架里“大模型辅助抽取和说明、确定性规则负责校验”的设计。
二、数据库怎么选？
1. 主数据库：推荐 PostgreSQL
主数据库负责保存：
- 报销单、发票结构化字段。
- 审核任务、状态和人工复核结果。
- 制度规则、科目映射和主数据。
- 历史记录、模型调用记录和证据引用。
优先选 PostgreSQL，是因为它可以同时承担业务数据存储，并通过 pgvector 扩展提供向量检索，初期能少维护一个服务。 pgvector 官方支持在 PostgreSQL 内保存和检索向量。pgvector 官方文档
如果你已经熟悉 MySQL，或者公司现有系统统一使用 MySQL，也完全可以采用 MySQL；这个项目没有必须使用 PostgreSQL 的业务限制。
两个实现细节很重要：
- 金额用数据库 NUMERIC/DECIMAL 和 Python Decimal，避免浮点误差。
- 防重复提交要设计幂等机制和数据库约束，不能只靠“先查询有没有重复”。
2. 向量库：看是否需要保留当前 Milvus 设计
你的框架已经专门设计了 Milvus，因此有两条合理路线：
路线	适用情况	建议
PostgreSQL＋pgvector	先完成项目闭环、减少部署组件	优先推荐，但需要调整当前向量库设计
PostgreSQL＋Milvus	要按现有框架实现，或专门学习独立向量库	保留，额外准备内存和运维环境


Milvus Standalone 官方列出的内存要求是 8GB 起、推荐 16GB，推荐 CPU 为 4 核及以上。这是 Milvus 服务自身的参考要求，不能当作整个开发电脑的总配置。Milvus 官方要求
预算余额、发票号精确查重放关系库；制度和案例的“语义相似检索”才放向量库。
3. Redis 和文件存储
组件	用途	初期是否必须
Redis	缓存、任务队列配套	简单串行演示可省；独立异步任务建议加入
本地文件目录	保存原始图片、PDF、报告	开发阶段够用
对象存储	集中保存附件，便于多实例访问和备份	正式部署建议使用


原始 PDF、图片建议放文件存储，数据库只保存文件地址、哈希、大小和业务关联。
三、大模型怎么选？
这里要区分 OCR、文本大模型、Embedding 模型，它们承担不同工作。
1. OCR：先解决“看清票据”
建议处理顺序：
1. 对可解析的电子文档，优先读取原始文本或结构化内容。
2. 对扫描件、拍照图片使用 OCR。
3. 对复杂表格、特殊排版，再考虑视觉大模型辅助。
可选方案：
方案	优点	代价
云票据 OCR API	接入较快，可测试专门的票据字段识别	按调用计费，需要允许材料上传
本地 PaddleOCR	可在本地处理，控制数据流向	需要自己处理预处理、版面和字段映射


PaddleOCR 提供 CPU 和 GPU 部署方式，因此使用本地 OCR 也不等于必须买显卡。PaddleOCR 官方安装说明
另外，识别出发票内容不代表完成发票验真；如果需要验真，还要单独接入相应票据服务。
2. 文本大模型：初期推荐 Qwen-Plus API
建议先将 Qwen-Plus 系列作为候选基线，承担：
- OCR 文本到 JSON 字段的抽取。
- 业务事由、费用类别的辅助判断。
- 从企业科目表中推荐候选科目。
- 根据已有规则结果生成审核说明。
接入时确认所选版本和地域支持的结构化输出方式；JSON Object 和 JSON Schema 支持范围不同。即使输出符合结构，也仍要做字段和业务校验。通义结构化输出文档
这是一套起步候选，不代表已经证明它对你的票据最好。 最终用实际样本比较：
- 发票号码、税号、金额的准确率。
- 缺字段时是否编造。
- JSON 输出是否稳定。
- 单张票据成本和处理时间。
- 需要人工复核的比例。
复杂图片可另测 Qwen-VL 系列；初期不必把每张票据都送进视觉大模型。
3. 本地模型：Qwen3-8B / 14B 可作为测试基线
如果数据不能出内网，可以从：
- Qwen3-8B：验证本地抽取和报告生成。
- Qwen3-14B：增加显存预算后，对照测试效果。
这两个是可验证的开源候选，不是“财务审核准确率保证”。8B 模型卡、14B 模型卡
项目第一阶段没有必要训练自己的大模型；先通过规则、检索和提示词完成业务闭环。
4. Embedding：需要语义检索时再加入
可以选 Qwen3-Embedding-0.6B 作为本地轻量候选，将制度条款转为向量，用于相似检索。官方模型卡
如果初期制度只有几十条、能按费用类型和职级直接查询，向量检索可以后置。
四、GPU 怎么选？
先决定是否本地部署模型，再决定显卡。
以下是针对单用户或低并发、短到中等上下文的工程估算起点，不是官方最低配置，也不是吞吐保证：
模型部署方式	GPU 建议
OCR 和大模型全部使用 API	不需要独立显卡
本地传统 OCR，文本大模型使用 API	先使用 CPU；速度不足再加 GPU
本地 8B 文本模型，4-bit 量化	12～16GB 显存作为测试起点
本地 14B 文本模型，4-bit 量化	24GB 显存更有余量
同时运行文本模型、视觉模型、Embedding	分开部署或排队运行，不能直接套用上述容量
多用户并发、长文档批处理	按压测选择更大显存或多卡


为什么显存需求不能只看“几 B”？
显存占用 ≈ 模型权重＋上下文缓存＋运行开销＋其他同时运行的模型。

例如，8B 模型按每参数 2 字节粗算，单权重就约 16GB；4-bit 量化可降低权重占用，但还需要缓存和运行空间。
显卡规格可以参考 RTX 4090 的 24GB、RTX 5090 的 32GB，但这些只是容量示例，具体采购还要结合预算、可获得型号及推理框架兼容性。4090 官方规格、5090 官方规格
当前阶段更建议先租卡验证本地效果，再决定是否采购。

七、比显卡更需要提前准备的东西
你这个项目真正影响“能否审核”的硬性依赖还有：
1. 可执行的企业制度：不同城市、职级、费用类型的标准。
2. 预算和历史入账数据：没有这些，只能演示，无法真实判断预算和重复报销。
3. 公司主数据和科目表：公司抬头、税号、员工、部门、项目、科目编码。
4. 已人工标注的票据样本：建议先整理 100～300 份，覆盖清晰、模糊、多页、重复和缺材料情况。
5. 数据处理边界：是否允许上传外部 API，决定云端还是内网部署。
6. 正式运行的权限、备份和审计机制：确保附件可追溯，人工复核有记录。
最终建议
以你现在“需求明确、代码尚未开始”的阶段，我建议：
32GB 内存电脑＋FastAPI＋PostgreSQL＋云票据 OCR 或本地 PaddleOCR＋Qwen-Plus API。
先完成上传、识别、规则校验、查重和人工复核闭环；需要制度语义检索时加入 pgvector。若学习目标要求严格落地现有 Milvus 设计，则保留 Milvus，并相应提高内存预算。GPU 暂缓采购。
