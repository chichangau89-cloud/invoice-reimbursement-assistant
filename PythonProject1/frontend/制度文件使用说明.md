# 制度文件检索

在项目根目录启动 `python main.py`，在另一终端启动 `python -m http.server 8080 --directory frontend`。修改后端代码后需先 Ctrl+C 停止原服务再启动；浏览器 Ctrl+F5 刷新。

点击左侧“制度文件”，页面会从 MySQL 读取当前已入库版本的 9 个制度板块（BX-00 至 BX-08）。点击任一板块后，后端按该板块的文件标识从 MySQL 读取完整条款，并在页面显示。目录和正文都会校验当前 `clauses.json`、MySQL 活跃记录和内容哈希一致，未完整同步的版本不会展示。

接口均为只读，不写入或修改制度数据：

- `GET /api/policies/documents`：返回 9 个制度板块目录及其同步状态。
- `GET /api/policies/documents/BX-02`：按板块读取一份制度文件的完整条款。
- `GET /api/policies/search?q=住宿费用报销标准&limit=5`：在展开的“按报销事项语义检索条款”中使用 Milvus 召回相关条款。

配置沿用项目根目录 `.env`：MILVUS_URI、MILVUS_TOKEN、MILVUS_COLLECTION、MYSQL_*、EMBEDDING_MODEL、EMBEDDING_PATH。当前导入版本的租户标识由 `policy_data/active.json` 管理；若设置 POLICY_TENANT_ID，必须与当前入库版本一致。此本地演示接口没有登录鉴权，不应直接暴露到公网。

需要的依赖列在 `requirements-policies.txt`。请使用启动后端的同一 Python 环境安装。向量模型仅从本地目录或缓存加载；已有模型可设置 EMBEDDING_PATH，不会在用户查询时自动下载。

召回使用与入库相同的 BGE 模型和查询前缀，按企业、policy 文档类型和模型过滤。之后从 MySQL 核对有效状态与 content_hash，只展示匹配的正文。没有记录会显示空结果；依赖、模型或数据库故障返回 503，不以本地样例伪装检索成功。

展示的是已入库的制度条款片段，不是原始 PDF 下载。相似度仅表示语义接近，不是审核通过率；demo-company 会明确标注教学数据。

发票预审会使用已验证的条款 JSON 执行确定性规则，并把制度版本、文件和条款位置返回给前端。当前制度状态为 `draft`，因此预审结果必须人工复核，不能自动批准付款。

## 多材料审核

顶部“上传材料”可一次选择最多 6 份 PDF、PNG、JPG 或 JPEG，包括发票、行程单/酒店水单和审批单。上传后调用 `POST /api/audits/documents` 创建材料案件；补充业务字段后，调用 `POST /api/audits/{case_id}/review` 生成审核报告。

报告分开显示三类依据：上传材料的识别与交叉校验、MySQL 中按租户/发票号码/开票日期的精确历史查重、Milvus 召回且由 MySQL 校验版本的制度候选。历史库或制度服务不可用时，结果会明确标出数据缺口，不能据此自动通过。
